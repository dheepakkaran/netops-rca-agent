Network operations · Kafka · Spark · PyTorch · Claude API

Thousands of alarms. One router to fix.

Router telemetry streams through Kafka, Spark and Cassandra. A PyTorch forecaster flags what is not normal and groups it into incidents. An agent reads the topology, the alarm lines and the runbooks, then names the router that caused it, or says it was noise. It recommends; it never touches the network.

03 · ANOMALY DETECTION

    
The forecaster finds every fault with a fifth of the false alarms.

    
The LSTM learns normal behaviour from the first two fault-free hours, one shared model for all routers, each input window centred on its own mean. An anomaly is a forecast error far above normal for two steps or more. Thresholds were tuned on the 4 development faults only.

Optimization, honestly: int8 made the model 2.4× smaller (22.8 → 9.5 KB) with identical detections, but scoring was slower on this CPU (0.84 s → 1.41 s). For a 32-unit LSTM, quantization helps size, not speed.

  






  

    
04 · ROOT CAUSE

    
The two rules fail exactly where the cause is quiet. The agent does not.

Where the rules break
F07 and F11 are BGP misconfigurations: the root only logs session flaps, while its victims lose packets. The detector flags the victims, so both rules name a victim. The agent gets symptom alarms from every router in the window, sees the shared uplink and reads its BGP lines.

      
Where it does not prove much
Both models scored 9/9, so this test cannot tell them apart. The network is a clean tree, the alarm text is templated, and there are 8 test faults. Real meshes, partial failures and vendor logs would be harder.

    

  






  

    
05 · MODEL ROUTING

    
Three models, each where it pays for itself.

    

    

      
haiku · once
Labeler
Names the 12 alarm clusters and marks each as symptom or noise: one call, $0.0007. Its answer is checked by code; Sonnet would redo it if the check failed.

      
sonnet · default
Investigator
Reads the evidence pack, calls read-only tools (1–3 per incident), submits the diagnosis. Matched Opus on every test incident at 60% lower cost.

      
opus · escalation
Second opinion
Called only when the investigator disagrees with the deterministic topology rule. On test: 2 of 9 incidents, 9/9 correct, $0.130 vs $0.223 for Opus on everything.*

    

    
* The escalation rule was chosen after seeing the test results (self-reported confidence never dropped below 0.7, so it was useless as a trigger). Its cost is therefore computed from the Sonnet and Opus test ledgers, not from a separate run. The system prompt and tools are identical for every incident, so 37.5% of all prompt tokens were cache reads.

  






  

    
06 · WHAT BROKE

    
Eight things went wrong or turned out weaker than hoped.

    

      
My metric could be gamed
The first LSTM run merged 4 faults into one giant incident, and my scorer counted it as finding all 4. Now a fault counts only if an incident starts inside it.

      
The daily curve looked like a fault
Trained on 2 hours, the forecaster flagged the normal traffic drift later in the day. Centring each window on its own mean fixed it.

      
Quantization: smaller, not faster
int8 cut the model 2.4× with the same detections but scored slower on CPU. Reported as is.

      
Confidence was useless for routing
The model was always 0.70–0.92 sure. Escalation now triggers on disagreement with a deterministic rule instead.

07 · RUN IT

    
Java from pixi, Python from uv, no Docker.

    
pixi install && uv sync
scripts/services.sh up                 # Kafka (KRaft) + Cassandra
uv run python -m netops.sim            # seeded network, faults, alarms
uv run python -m netops.produce        # → Kafka
uv run python -m netops.stream         # Spark: Kafka → Cassandra
uv run python -m netops.detect         # LSTM vs z-score, int8, incidents
uv run python -m netops.textmine       # alarm clusters
uv run python -m netops.agent test routed   # ANTHROPIC_API_KEY in .env
uv run python -m netops.report         # RESULTS.md from results/
